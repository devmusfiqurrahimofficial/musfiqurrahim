# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A personal portfolio site styled as a macOS desktop (menu bar, dock, draggable windows), plus an admin panel and an Express API for editing its content. React 19 + Vite 8 + Tailwind CSS v4 + Redux Toolkit, plain JSX (no TypeScript); the frontend lives in `client/` and the server in `server/` (plain Node.js ES modules); each has its own `package.json` and `node_modules`. Icons come from `lucide-react`; brand logos (GitHub, LinkedIn) are hand-written SVGs in `client/src/components/BrandIcons.jsx`.

## Commands

Run from the repo root (the root `package.json` only forwards to `client/` and `server/`), or run the same script inside the folder.

- `npm run install:all` — `npm install` in both `client/` and `server/`
- `npm run dev` — Vite dev server (portfolio at `/`, admin at `/admin`); proxies `/api` to port 4000
- `npm run dev:server` — API server with `node --watch` (needs MongoDB and `server/.env`; see `server/.env.example`)

Two env files, both gitignored: `client/.env` holds the `VITE_FIREBASE_*` web config the admin panel signs in with (it's baked into the admin bundle; Vite needs a restart after changes), and `server/.env` holds the server settings. Each has a committed `.env.example`.
- `npm run build` — production build to `client/dist/` (the admin is a separate lazy-loaded chunk)
- `npm start` — production: the Express server serves `/api` and the built `client/dist/`
- `npm run preview` — serve the built `client/dist/` without the API
- `npm test` — Vitest, once (`client/`; tests are `*.test.js` next to the code)

**Layout.** `client/src`: `main.jsx` (Provider, PersistGate, router), `App.jsx` (desktop), `apps/` (window contents, plus `registry.js`), `components/` (desktop chrome), `store/` (store setup, hooks, listener middleware, custom middleware), `features/<feature>/` (slices, selectors, thunks, RTK Query endpoints, listeners), `config/` (`apiUrl.js`, `siteText.js`), `admin/` (admin app, with `pages/`), `data.js`. `server/src`: `index.js` (app + startup), `config/`, `db/` (connection, collections), `models/` (validation schemas), `middleware/` (auth, rate limit), `routes/`, `services/` (SSE events), `utils/` (validation helpers). Frontend paths below are relative to `client/`, backend paths to `server/`.

Tests use Vitest (`client/src/**/*.test.js`): slices and selectors as plain functions, and `store/store.test.js` against a real store from `setupStore()` with `fetch` stubbed. There is no linter or formatter.

## Architecture

**State is Redux Toolkit, one store** (`src/store/`). There is no React Context. `setupStore.js` builds it (`configureStore`; middleware order: listener middleware, RTK Query, the custom `errorReporter`, and `redux-logger` in dev only), `index.js` makes the app's instance, persists it and dispatches `appStarted` once saved state is back. `rootReducer.js` uses `combineSlices`; `redux-persist` wraps only `settings` (theme) and `content` (its `data`). Components read through selectors with `useAppSelector`/`useAppDispatch` from `store/hooks.js`, never `state.x` directly, and keep only local UI state (form drafts, open folders, hover) in `useState`. Each feature folder holds what applies of `<feature>Slice.js`, `<feature>Selectors.js`, `<feature>Thunks.js`, `<feature>Api.js` (RTK Query via `apiSlice.injectEndpoints`) and `<feature>Listeners.js` (side effects through `startAppListening`, imported for effect in `setupStore.js`, or by `AdminApp` for admin-only ones). Rules of thumb:
- Server state for the admin is RTK Query (`features/api/apiSlice.js`; projects, skill groups and commands share `collectionEndpoints()`, which mirrors the server's `collectionRouter`). Deletes and reorders are optimistic with undo; saves write the server's answer into the cached list (no refetch, so other items keep their identity and editors' drafts survive).
- Thunks are for orchestration or what RTK Query can't do: public content (persisted, with a bundled fallback), Firebase auth, image upload, the contact form's mailto fallback.
- Side effects (DOM theme, EventSource, timers, toasts, redirects on 401) live in listeners, not components.
- Errors: `errorsListeners.js` logs failed RTK Query mutations (except 401/403 and 422 field errors, which forms show inline) and thunks that reject with `{ message, notify: true }` into the `errors` reducer; each logged error becomes a toast. Success toasts come from `features/notifications/successMessages.js`, keyed by endpoint name or thunk type.
- `dispatch(confirm({...}))` (`features/dialog/dialogThunks.js`) resolves to the user's answer.
- Admin-only code (the `auth` slice, injected with `injectInto(rootReducer)`; Firebase in `features/auth/firebase.js`) is imported only from the lazy admin chunk. Core code reacts to `signedOut` from `features/auth/authActions.js`. The Firebase ID token reaches requests through the thunk extraArgument (`store/services.js`).

**Content vs. UI.** The wallpaper is `client/public/wallpaper.jpg`. Portfolio content (profile, bio, socials, projects, skills, tools) is stored in MongoDB, served by the API and edited through the admin panel. The `content` feature holds it: `fetchPortfolio` stores the `/api/portfolio` response, persisted as `persist:content`, and `contentSelectors.js` falls back to the bundled `src/data.js` until the API has ever answered. So the page renders at once with the last saved content (or the bundle on a first visit), and if the API is unreachable that content stays, so a static-only deploy still works. Components read content through the selectors in `contentSelectors.js`, never by importing `data.js` directly (only `previewOf` is imported from it). `data.js` is only that fallback; the server never writes it to the database, and edits there don't reach the API. The Terminal app reads the same data for `whoami`, `projects`, `skills`.

**Window manager is the `windows` feature.** `features/windows/appList.js` lists the apps as plain data (`id`, `title`, default `w`/`h`); `src/apps/registry.js` adds the icon, dock gradient and component. Window state is an entity adapter keyed by app id (`open`, `minimized`, `maximized`, `z`, `x`, `y`, `w`, `h`) plus a rising `zTop`; the active window is derived (`selectActiveId`) as the visible window with the highest `z`. `dispatch(openApp(id))` (`windowsThunks.js`, which works out placement from the screen size) is the one entry point for launching or restoring a window; components dispatch it themselves, nothing is passed down as props. A listener bounces the dock icon on launch.

**Adding an app** means: create a component in `src/apps/`, add it to `APP_LIST` in `features/windows/appList.js` and to `VIEW` in `src/apps/registry.js`. The Terminal's `open` command reads `APP_IDS` from `appList.js`.

**`src/components/Window.jsx`** renders the chrome (traffic lights, title bar), handles pointer-capture dragging with clamping, and drives open/close/minimize animations. `MENU_H` and `DOCK_SPACE` in `features/windows/layout.js` are used for window placement — keep them in sync with the actual menu bar and dock sizes. Close is delayed ~170ms so the close animation plays before the window unmounts.

**Mobile.** `isMobile` in the `ui` slice (max-width 767px, kept current by `uiListeners.js`) forces every window maximized, makes desktop icons single-tap instead of double-click, and switches the dock to compact mode.

**Styling.** Tailwind v4 via `@tailwindcss/vite` — there is no `tailwind.config.js`. Theme tokens (fonts, custom animations/keyframes such as `animate-window-open`, `animate-dock-bounce`) are defined in the `@theme` block of `src/index.css`; the liquid-glass materials (`.glass` for the dock and icons, `.glass-panel` for anything holding text) are plain CSS below it — see the comment there. Text selection is disabled globally; add the `selectable` class (or use an input) to re-enable it. Use `scroll-thin` for scrollable panes.

**Project previews.** Each card shows `public/projects/<slug>.webp` (path from `previewOf()` in `data.js`), falling back to the project's `color` gradient if the file is missing. `npm run screenshots` regenerates them with headless Chromium + ImageMagick; pass project names to redo only those. Re-run it after adding a project or renaming one (the filename is derived from `name`).

**Site text.** The browser tab title, the Contact heading and intro, and the Skills "tools" heading are profile fields (`siteTitle`, `contactTitle`, `contactText`, `toolsTitle`). Empty means the default in `src/config/siteText.js`, which the admin's Profile page also shows as placeholders.

**Contact form** POSTs to `/api/messages` (`submitContactForm` in `features/contact/`), which the admin reads under Messages. It falls back to a `mailto:` URL to `profile.email` only when the API is unreachable or answers without JSON (static-only deploy). A hidden `website` field is a honeypot.

**Live updates.** After the first successful `/api/portfolio` fetch, `contentListeners.js` opens an `EventSource` on `/api/events` and refetches (debounced) on each `content` event, so admin saves show up in open portfolio tabs without a reload. It also refetches when the stream reconnects, since saves made while it was down sent no event. On the server, `touch()` in `server/src/db/index.js` both records `meta.updatedAt` and broadcasts that event (`server/src/services/events.js`). Any new write to public content must call `touch()`.

**Terminal custom commands** come from `commands` in the portfolio data. Built-ins are checked first; the server also refuses built-in names (`RESERVED_COMMANDS` in `server/src/models/schemas.js`). Keep that list in sync when adding a built-in to `src/apps/Terminal.jsx`.

**Dark mode** is derived (`selectIsDark`): the saved choice in `settings.theme`, or light while there is none (the system setting is ignored). `settingsListeners.js` applies it to `<html>`; `public/theme.js`, loaded as a blocking script from `index.html`, reads `persist:settings` to avoid a flash on load (a file, not an inline script, because the CSP forbids inline scripts).

**Theme.** The sky-blue liquid glass lives in `src/index.css`: `.glass` (dock, icons), `.glass-panel` (windows, menus, admin window) and `.glass-bar` (menu bar). Shadow colour comes from `--glass-shadow` so dark mode can swap it. Windows override `--glass-drop` with `rgb(var(--glass-shadow) / a)` for active and inactive depth. Inside the admin window, `.settings-pane .glass-panel` flattens nested panels (no second blur); dialogs keep full glass.

## Backend (`server/`)

Express 5 (async errors reach the error handler without try/catch), MongoDB through the official `mongodb` driver (no Mongoose: `src/models/schemas.js` is the only place fields are defined). `src/index.js` connects first and exits with a clear message if MongoDB is unreachable (`MONGODB_URI`, default `mongodb://127.0.0.1:27017/portfolio`).

**Data model** (`src/db/index.js`): collections `projects`, `skills` (one document per skill group), `commands` (custom Terminal commands, unique `name`), `messages` (contact form; admin-only), `uploads` (admin-uploaded images: `POST /api/uploads`, via the `uploadImage` thunk in `src/features/uploads/`; served publicly by `GET /api/uploads/:id` and linked by absolute URL so they work from another domain. The stored type comes from the file's first bytes, not the browser's claim. `touch()` also runs `pruneUploads()`, which deletes uploads more than a day old that neither `profile.image` nor any project's `image` links to) and `settings`, which holds single documents with string ids: `profile`, `tools` (`{ tools: [] }`) and `meta` (`updatedAt`, bumped by `touch()` after every write). Projects and skill groups carry an internal `order` field. `toApi()` turns `_id` into a string `id` and hides `order`, so the frontend never sees Mongo types. `parseId()` turns malformed ids into 404s.

**No seeding.** The server never writes content on its own; a new database starts empty and is filled through the admin panel. Until a profile is saved, `/api/profile` and `/api/portfolio` return an empty one (`name`, `bio`, `stats`, `socials`) so the site's lists still render.

The database name comes from the URI path; if the URI has none (typical for Atlas `mongodb+srv://…/`), it's `MONGODB_DB` or else `portfolio`.

**Kernel caveat:** MongoDB 8.0+ won't start on Linux kernels 6.19–7.0.13 (SERVER-121912, an allocator/rseq bug). On such a machine, run MongoDB 7.0 locally, e.g. `podman run -d --name portfolio-mongo -p 127.0.0.1:27017:27017 -v portfolio-mongo:/data/db docker.io/library/mongo:7.0`, or use Atlas.

- **Auth is Firebase.** The admin panel signs in with the Firebase JS SDK (email/password only) and sends the Firebase ID token as `Authorization: Bearer`. `requireAuth` (in `src/middleware/auth.js`) verifies it with `firebase-admin`, which needs only `FIREBASE_PROJECT_ID`, no service-account key, and then applies `isAdmin()`. A valid token alone is not enough, since anyone can sign in to the project with Google. Access comes from `ADMIN_UIDS`, or from `ADMIN_EMAILS` when Firebase has verified the email. The server refuses to start without one of them. Failures return 401 (bad or expired token) or 403 (valid, but not allowed). `GET /api/auth/me` is the only auth route. Passwords, resets and sessions belong to Firebase; the server stores no users.
- **Routes:** public `GET`s for `/api/portfolio` (includes `commands`), `/api/profile`, `/api/projects`, `/api/skills`, `/api/tools`, `/api/commands` and `/api/events` (SSE). Projects, skill groups and commands use `collectionRouter(collection, schema)` in `routes/content.js`: list/get/create/`PUT` replace/`PATCH` merge/delete, plus `POST /reorder` with `{ ids }`, which rewrites `order` in one `bulkWrite`. `POST /api/mail` (admin-only) emails the profile's contact `email` through `services/mailer.js` (needs `SMTP_*`). `/api/messages` (`routes/messages.js`): `POST` is public and rate-limited (5 per 10 minutes per IP, `src/middleware/rateLimit.js`; set `TRUST_PROXY` behind a proxy, parsed in `config/` because Express reads the string `"1"` as an IP), while `GET`/`PATCH {read}`/`DELETE` are admin-only. All of `/api` also has a 300-per-minute-per-IP ceiling, and `/api/events` allows 20 open streams per IP.
- **Headers:** every response gets `nosniff`, `X-Frame-Options: DENY` and a `Referrer-Policy`; `/api` responses get `Content-Security-Policy: default-src 'none'`, and HSTS is sent when `NODE_ENV=production`.
- **Writes are protected by default:** a guard in `index.js` runs `requireAuth` on every non-GET `/api` request unless it's in `PUBLIC_WRITES` (only `POST /api/messages`). Routers still call `requireAuth` themselves; it skips re-verifying when `req.user` is already set. Mongo duplicate-key errors (code 11000) become 422 `{ field: 'is already used' }`.
- **Validation:** every write goes through `validate(schema, body)` with the schemas in `src/models/schemas.js`. Unknown fields are dropped. Failures return 422 with `details` keyed by field, which the admin forms show inline. Only schema keys are ever written, so request bodies can't inject Mongo operators or extra fields. URLs must be http(s) or a root-relative path.

## Deployment

The site is on Vercel (project root directory `client`, static `dist/`, SPA rewrite in `client/vercel.json`); the API runs separately on Render (`render.yaml`, `rootDir: server`) against MongoDB Atlas. Vercel builds with `VITE_API_URL` set to the Render URL, and the API's `CORS_ORIGIN` lists the site's domains. Render's free tier sleeps when idle, so the first request can take ~50s; the portfolio shows the last content it saw (or the bundled `data.js`) meanwhile. Nothing may be stored on the Render disk (it's wiped on restart), which is why uploads live in MongoDB.

`client/vercel.json` also sets the site's security headers, including a Content-Security-Policy that names the Render API URL (`connect-src`) and the Firebase `authDomain` (`frame-src`; `apis.google.com` in `script-src` is Firebase's auth iframe loader). If either changes, or the site starts loading something from a new origin, update the CSP or the browser will block it.

## Routing

One page (`client/index.html`) and one React Router app, set up in `src/main.jsx`: `/` is the portfolio, `/admin/*` lazy-loads `src/admin/AdminApp.jsx` (so Firebase never reaches visitors), and anything else redirects to `/`. Both share the one store, provided above the router. The portfolio itself has no routes; its windows are state, not URLs. Because paths like `/admin/projects` must load `index.html`, the Express server falls back to it for any GET without a file extension (Vite's dev and preview servers already do this). A static host needs the same rewrite; for Vercel it's in `client/vercel.json`, which also skips `/api/` and sends the admin's `noindex` header.

## Admin panel (`src/admin/`)

`AdminApp` starts the session watch (`watchAuthState`) and defines nested routes relative to `/admin`: `login`, then everything else behind `RequireAdmin`, the private route. While the session is being checked it shows a spinner; when signed out it redirects to `/admin/login` with `state.from`, and `LoginRoute` sends the user back there once signed in. Pages are children of the `Shell` layout (rendered through `<Outlet />`), one per `NAV` entry: `dashboard` is the index route, the rest are `/admin/<id>`; build links with `pathOf(id)`. Old `/admin/#/<id>` bookmarks are redirected. The admin sets its own document title and a `noindex` meta tag, and the server also sends `X-Robots-Tag: noindex` under `/admin`. The guard only controls what the UI shows; the API still checks the token on every write. `features/auth/firebase.js` initialises Firebase from `VITE_FIREBASE_*` (`auth` is null if any are missing, and the login screen lists them), and maps Firebase error codes to messages. `watchAuthState` follows `onAuthStateChanged`; for each Firebase user the `verifySession` thunk calls `/api/auth/me`, and on rejection (or any later 401/403, see `authListeners.js`) `endSession` signs out of Firebase and the login screen shows the server's message. Signing out also resets the RTK Query cache. Every request gets a fresh ID token from `auth.currentUser.getIdToken()`; Firebase handles refresh and storage. Pages use the RTK Query hooks from `features/*/…Api.js`; the unread badge and the Messages page share one polled `getMessages` cache entry, normalized with an entity adapter. `ui.jsx` holds the shared glass components (`Panel`, `Button`, `Field`, `TagInput`, `Modal`) and the store-connected `Toaster` and `ConfirmDialog`. `useDragSort.js` is the pointer-based drag-to-reorder hook (the Projects page uses it; Skills and Commands still use up/down buttons). It hands the full id list to a `reorder…` mutation.

**Project colours** must come from `src/admin/gradients.js`. Tailwind only generates classes it finds in the source, so a gradient that isn't listed there (or in `data.js`) won't render. The server only checks the `from-x-N to-y-N` shape.
